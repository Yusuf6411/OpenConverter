## Phase 1: Foundations
- [~] M1.1 oc-core: errors with stable codes and CLI exit codes, notes, limits, progress/cancel token, option schemas with validation, format descriptors with magic-byte sniffers, registry and Dijkstra route planner (17 unit tests). Not yet done: the IR types (Image, Audio, Video, Document, ...) are deferred to the milestone that first needs each one; `Registry::detect` has no test yet.
- [~] M1.2 oc-io: checked ByteReader, BitReader/BitWriter (MSB/LSB, round-trip tested); oc-checksum: CRC-32, CRC-32C, CRC-64/XZ, Adler-32, xxHash64 against published check values (scalar only; SIMD paths and bounded stream sinks are not written yet).
- [~] M1.3 oc-compress: DEFLATE inflate (bomb limit, cancellation, never panics on garbage fuzz loop) and deflate (levels 0-9, stored/fixed/dynamic blocks), zlib, gzip (multi-member), PackBits, LZW (GIF and TIFF flavours). Checked against CPython: a level-9 dynamic-Huffman stream decodes correctly, and our zlib/gzip output at levels 1, 6, 9 is accepted by Python. Measured with Python as reference: on a 200 kB 6-bit-noise input our level 6 output is 154,622 bytes vs zlib 151,443 (2% larger); on repetitive text we are smaller. Not done: speed tuning (the inflate Huffman decoder is bit-by-bit), the Windows-only budget measurements, and the LZW GIF/TIFF vectors from real files (only round trips so far).
- [~] M1.4 oc-text: UTF-8/16/32, ASCII, ISO-8859-1, windows-1252, BOM and heuristic detection, strict/replace policies with loss notes, line-ending detect/convert (6 tests). Not done: other legacy code pages (Shift-JIS, GBK, ISO-8859-2.., windows-125x) and Unicode normalisation (NFC/NFD), which need mapping data. oc-xml: pull parser with namespaces, char references, CDATA, comments, PIs; entity declarations and DOCTYPE internal subsets rejected (no XXE or entity bombs); depth and attribute limits; writer with escaping (8 tests, including a garbage loop and an entity-bomb test). Not done: DTD attribute defaults, `encoding=` re-decoding, line-ending normalisation inside the parser.
- [~] M1.6 (done before M1.5) oc-engine + oc-cli: text conversion end to end (`openconverter convert in.txt out.txt --set to_encoding=utf-16le --set line_ending=lf --set bom=true`, `formats [--json]`, `--version`), typed exit codes, no-overwrite by default, atomic output write, notes printed to stderr (4 engine tests; CLI exercised by hand). Not done: `info`, `routes`, `doctor`, `--explain`, completions, JSON result output; progress is only reported at 3 coarse steps.
- [~] M1.5 worker isolation (oc-engine `isolated`, `openconverter __worker`): each CLI conversion runs in a child process with a wall-clock timeout, cancellation that kills the child, a Unix address-space cap (`ulimit -v`, default 4 GB) and typed error codes passed back through the exit status. Tests prove a panicking worker, an infinite loop, a cancellation and (on Linux) a runaway allocation are all contained and reported as `worker_crashed`, `timeout`, `cancelled`. Not done: a Windows memory cap (job objects), a macOS memory cap (RLIMIT_AS is not enforced there), Linux landlock/seccomp sandboxing, and a persistent worker pool (one process per conversion today).
- [~] M1.7 fuzzing: cargo-fuzz targets for inflate, zlib, gzip, lzw, packbits, xml, text and a deflate round trip (`fuzz/`, nightly toolchain). Ran each for 25 seconds locally with no crash (about 120k to 950k runs each). That is a smoke test, not coverage: the nightly workflow (300 s per target) is written but has not run yet. `corpora/manifest.toml` exists but is empty. The release workflow skeleton is not written.

## Phase 2: Images
- [~] M2.1 oc-image IR (`Image`: gray/gray+alpha/RGB/RGBA at 8 or 16 bits, dpi, ICC profile, text) and ops: depth and layout conversion (alpha flattening and colour-to-gray report notes), nearest/bilinear resize, flips, 90/180/270 rotation. Not done: colour management (ICC profiles are carried, never applied), Lanczos/bicubic resampling, tiling above the 64 MP in-memory limit, animation frames.
- [~] M2.2 codecs written from the specifications, each decoder using only checked reads:
  - PNG: all colour types and bit depths, Adam7, tRNS, PLTE, CRC checks, pHYs/tEXt/iCCP; encoder with adaptive filtering and levels 0-9. Decoded output matches Pillow's 8-bit RGBA for 14 variants, ImageMagick's raw 16-bit dumps, and the 1.x fixtures; our PNG output decodes identically in Pillow. APNG is detected and only the first frame is read (note emitted).
  - BMP: core/INFO/V4/V5 headers, 1/4/8/16/24/32 bpp, bitfields, RLE4/RLE8, top-down and bottom-up; encoder writes 24-bit, or 32-bit with a V4 header when there is transparency. Checked against ImageMagick-written files, Pillow-decoded dumps and hand-built 16-bit and top-down files. Not supported (typed error): JPEG/PNG-in-BMP, OS/2 Huffman and RLE24.
  - TGA: types 1/2/3/9/10/11, 8/15/16/24/32 bpp, all four origins; encoder writes 24/32-bit or 8-bit gray, raw or RLE. Checked against 16 Pillow-written files and hand-built 15/16-bit and right-to-left files.
  - GIF: first frame of 87a/89a files (interlaced, local/global palettes, transparency; later frames are skipped with a note, since the image model has no frames yet); encoder writes an exact palette up to 256 colours, otherwise median-cut with optional Floyd-Steinberg dithering, with loss notes for quantisation and for rounding partial alpha. Checked against 9 Pillow-written files; our files open in Pillow and ImageMagick. The shared quantiser is in `oc-image::quant`.
  - JPEG: decoder for baseline, extended-sequential and progressive Huffman files, 1/3/4 components, any integral chroma subsampling, restart intervals, JFIF dpi, ICC profiles, Adobe RGB/YCCK/CMYK. It uses libjpeg's integer IDCT, fancy upsampling and fixed-point colour maths, and its output is byte-identical to libjpeg (via Pillow) on all 24 fixtures: 4:4:4, 4:2:2, 4:2:0, 4:4:0, progressive, optimised tables, restart markers by block and by row, gray, CMYK, quality 10 and 100, sizes from 1x1 to 131x97. Truncated data decodes as far as it goes with a warning. Encoder: baseline with the standard tables, 4:4:4/4:2:2/4:2:0, quality 1-100; file sizes are within 5% of libjpeg's and PSNR within 0.3 dB on the same input, and libjpeg decodes our files to exactly the pixels our own decoder gives. Not supported (typed error): arithmetic coding, lossless and hierarchical JPEG, 12-bit samples, non-integral subsampling ratios. EXIF orientation is reported in a note and not applied. Not done: progressive and optimised-Huffman encoding, restart markers on output, EXIF/XMP carry-over.
  - ICO/CUR: reads the largest image, stored as PNG or as a DIB (1/4/8/24/32-bit, with the AND mask, and old 32-bit icons whose alpha byte is unused); writes PNG-compressed entries at the requested square sizes (`sizes=16,32,48,256`), or the image's own size, for ICO and CUR (hotspot 0,0). Checked against 5 Pillow/ImageMagick files; Pillow and ImageMagick read ours. Not done: choosing which size to read, writing DIB entries for pre-Vista readers, ICNS.
  - TIFF (`tif`/`tiff`, little and big endian, classic only): reads strips and tiles, none/LZW/Deflate/PackBits, horizontal predictor (8 and 16 bit), bilevel/gray/palette/RGB/RGBA/CMYK (converted to RGB with a note), 1-16 bits per sample, extra alpha (unpremultiplied with a note), dpi and ICC; first page only (note), orientation reported not applied, truncated data decodes as far as it goes with a warning. Writer: gray/gray+alpha/RGB/RGBA at 8 or 16 bits, `compression=none|lzw|deflate|packbits` (default lzw) and `predictor` (default on), dpi and ICC. Pixel-identical to libtiff (via ImageMagick) on 32 fixtures; Pillow and ImageMagick read our files. Not done: BigTIFF, JPEG-in-TIFF, tiled output, multi-page output, CCITT fax.
  - WebP (`webp`): lossless (VP8L) and lossy (VP8 key frames, in the new `oc-vp8` crate). Lossless: the full decoder (all four transforms, colour cache, meta prefix images, LZ77 with the 2-D distance map, simple and normal prefix codes, ICC from an extended header) is pixel-identical to libwebp (via Pillow) on 27 files made with methods 0-6, qualities 0-100, palettes of 2-256 colours, alpha with and without `exact`, and sizes from 1x1 to 262x194. The encoder writes subtract-green, per-tile predictors chosen against the running residual statistics (libwebp's approach, with its near-zero bias), per-tile cross-colour multipliers, palettes with 1/2/4/8-bit pixel packing, hash-chain LZ77 with a cost-model parse, a colour cache sized by estimate, and tile-wise prefix code groups from clustering; `effort` 0-6 and `clean_transparent` are the options. Our output decodes to the identical pixels in libwebp (Pillow) in 259 of 259 combinations (27 fixtures, random and structured pictures, efforts 0-6, 1xN/Nx1/gray/palette inputs). Size against libwebp at its default method 4 on six pictures (800x600 screenshots, noisy and smooth 1-2 MP photographs): +0.5% in total at effort 4 (screenshots +1-3%, noisy photo +2.8%, smooth photo -3%) and +1.3% against its method 6 at our effort 6. Speed: a 1.9 MP photograph encodes in about 1.0 s at effort 4 and decodes in about 0.1 s. A fuzz target covers the decoder and another the encoder round trip.
    Lossy decode: `oc-vp8` implements RFC 6386 key frames (boolean decoder, segments, token partitions, all intra modes, the WHT and DCT, simple and normal loop filters) and matches libwebp's `WebPDecodeYUV` plane for plane on 51 files made by libwebp through Pillow and ImageMagick (qualities 5-100, methods 0-6, 1-4 segments, 1-8 partitions, filter type, strength and sharpness variants, sizes 1x1 to 200x150). `oc-image` adds libwebp's fancy chroma upsampling and its integer YUV to RGB, plus `ALPH` (raw or lossless-coded, all four prediction filters), and is pixel-identical to Pillow on 36 more files including alpha. The tables of the format were read once from a libwebp binary by a documented script (ADR-0004).
    Lossy encode (`lossless=false`, `quality` 0-100, `effort` 0-6): RGB to 4:2:0 with libwebp's coefficients, per-macroblock choice between four 16x16 modes and ten 4x4 modes per sub-block by distortion plus an estimated rate taken from the token probabilities that end up in the stream (a second pass refines the estimate at effort 4 and up), dead-zone quantisation, optimal probability updates, skip flags, 1-8 token partitions, and a loop-filter level searched by reconstruction error. Alpha goes in an `ALPH` chunk coded with the VP8L encoder and the best of four prediction filters; fully transparent 8x8 blocks are flattened. The decoder reproduces the encoder's own reconstruction exactly, and libwebp (via Pillow) decodes our files, alpha exactly. Against libwebp at equal PSNR on six pictures (three screenshots, three photographs) at qualities 15-90, our files are 4.0% smaller than its method 4 and 2.5% smaller than its method 6 (screenshots -6% to +1.5%, photographs -3% to -8%). A 1.9 MP photograph encodes in about 0.6 s at effort 4 including the PNG decode. Fuzzing: `vp8` (raw key frames) and `webp_lossy_roundtrip` ran 90-120 s each; the first run found an integer overflow in the inverse DCT on corrupt coefficients, now wrapping like libwebp's C code.
    Not done: animation, EXIF/XMP carry-over, trellis quantisation and per-segment quantisers (libwebp's SNS) in the lossy encoder, lossy alpha (`alpha_quality`), a palette-ordering search beyond first-seen and sorted and predictor transform on palette indices in the lossless one.
  - QOI and Netpbm (P1-P7; writer picks PBM/PGM/PPM/PAM from the output extension, PAM when there is real transparency).
  Not done yet: animation (GIF/APNG/WebP frames), ICNS, SVG rasterisation (M2.3 onward).
- [~] M2.5 engine and CLI: `openconverter convert a.png b.bmp` (and between png, bmp, tga, qoi, pnm, gif, jpeg, ico, tiff, webp) work end to end, through the worker process. Writer options: `width`, `height`, `rotate`, `flip`, `background`, plus `level`/`adaptive_filter` (PNG), `rle` (TGA), `ascii` (Netpbm), `dither`/`interlace` (GIF), `quality`/`subsampling` (JPEG), `sizes` (ICO), `compression`/`predictor` (TIFF), `lossless`/`quality`/`effort`/`clean_transparent` (WebP). The file's content wins over its extension (mismatch is a warning). Metadata that the target cannot hold is reported as a loss note. Tested by converting every format pair through the engine and by checking CLI output with Pillow and ImageMagick.
- [~] Fuzzing: targets for png, bmp, tga, qoi, netpbm and an image round trip, seeded with the fixtures and run for 40-60 s each locally without a crash. The nightly workflow lists them but has not run.
- Performance has not been measured: layout conversion costs roughly 100 ns per pixel in debug builds, and a 1.8 MP BMP takes about 0.4 s to decode in a fuzz build. Release-build timings on a 3 MP picture: PNG to JPEG 0.2 s, JPEG to PNG 1.7 s (PNG encoding at level 6 dominates), PNG to BMP 0.17 s. That is acceptable for correctness work and is to be fixed in the performance milestones (SIMD, M1.2 leftovers).

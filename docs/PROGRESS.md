## Phase 1: Foundations
- [~] M1.1 oc-core: errors with stable codes and CLI exit codes, notes, limits, progress/cancel token, option schemas with validation, format descriptors with magic-byte sniffers, registry and Dijkstra route planner (17 unit tests). Not yet done: the IR types (Image, Audio, Video, Document, ...) are deferred to the milestone that first needs each one; `Registry::detect` has no test yet.
- [~] M1.2 oc-io: checked ByteReader, BitReader/BitWriter (MSB/LSB, round-trip tested); oc-checksum: CRC-32, CRC-32C, CRC-64/XZ, Adler-32, xxHash64 against published check values (scalar only; SIMD paths and bounded stream sinks are not written yet).
- [~] M1.3 oc-compress: DEFLATE inflate (bomb limit, cancellation, never panics on garbage fuzz loop) and deflate (levels 0-9, stored/fixed/dynamic blocks), zlib, gzip (multi-member), PackBits, LZW (GIF and TIFF flavours). Checked against CPython: a level-9 dynamic-Huffman stream decodes correctly, and our zlib/gzip output at levels 1, 6, 9 is accepted by Python. Measured with Python as reference: on a 200 kB 6-bit-noise input our level 6 output is 154,622 bytes vs zlib 151,443 (2% larger); on repetitive text we are smaller. Not done: speed tuning (the inflate Huffman decoder is bit-by-bit), the Windows-only budget measurements, and the LZW GIF/TIFF vectors from real files (only round trips so far).
- [~] M1.4 oc-text: UTF-8/16/32, ASCII, ISO-8859-1, windows-1252, BOM and heuristic detection, strict/replace policies with loss notes, line-ending detect/convert (6 tests). Not done: other legacy code pages (Shift-JIS, GBK, ISO-8859-2.., windows-125x) and Unicode normalisation (NFC/NFD), which need mapping data. oc-xml: pull parser with namespaces, char references, CDATA, comments, PIs; entity declarations and DOCTYPE internal subsets rejected (no XXE or entity bombs); depth and attribute limits; writer with escaping (8 tests, including a garbage loop and an entity-bomb test). Not done: DTD attribute defaults, `encoding=` re-decoding, line-ending normalisation inside the parser.
- [~] M1.6 (done before M1.5) oc-engine + oc-cli: text conversion end to end (`openconverter convert in.txt out.txt --set to_encoding=utf-16le --set line_ending=lf --set bom=true`, `formats [--json]`, `--version`), typed exit codes, no-overwrite by default, atomic output write, notes printed to stderr (4 engine tests; CLI exercised by hand). Not done: `info`, `routes`, `doctor`, `--explain`, completions, JSON result output; progress is only reported at 3 coarse steps.
- [~] M1.5 worker isolation (oc-engine `isolated`, `openconverter __worker`): each CLI conversion runs in a child process with a wall-clock timeout, cancellation that kills the child, a Unix address-space cap (`ulimit -v`, default 4 GB) and typed error codes passed back through the exit status. Tests prove a panicking worker, an infinite loop, a cancellation and (on Linux) a runaway allocation are all contained and reported as `worker_crashed`, `timeout`, `cancelled`. Not done: a Windows memory cap (job objects), a macOS memory cap (RLIMIT_AS is not enforced there), Linux landlock/seccomp sandboxing, and a persistent worker pool (one process per conversion today).
- [~] M1.7 fuzzing: cargo-fuzz targets for inflate, zlib, gzip, lzw, packbits, xml, text and a deflate round trip (`fuzz/`, nightly toolchain). Ran each for 25 seconds locally with no crash (about 120k to 950k runs each). That is a smoke test, not coverage: the nightly workflow (300 s per target) is written but has not run yet. `corpora/manifest.toml` exists but is empty. The release workflow skeleton is not written.

## Phase 2: Images
- [~] M2.1 oc-image IR (`Image`: gray/gray+alpha/RGB/RGBA at 8 or 16 bits, dpi, ICC profile, text) and ops: depth and layout conversion (alpha flattening and colour-to-gray report notes), nearest/bilinear resize, flips, 90/180/270 rotation. Colour management is below. Not done: Lanczos/bicubic resampling, tiling above the 64 MP in-memory limit.
- [~] M2.2 codecs written from the specifications, each decoder using only checked reads:
  - PNG: all colour types and bit depths, Adam7, tRNS, PLTE, CRC checks, pHYs/tEXt/iCCP; encoder with adaptive filtering and levels 0-9. Decoded output matches Pillow's 8-bit RGBA for 14 variants, ImageMagick's raw 16-bit dumps, and the 1.x fixtures; our PNG output decodes identically in Pillow. APNG is detected and only the first frame is read (note emitted).
  - BMP: core/INFO/V4/V5 headers, 1/4/8/16/24/32 bpp, bitfields, RLE4/RLE8, top-down and bottom-up; encoder writes 24-bit, or 32-bit with a V4 header when there is transparency. Checked against ImageMagick-written files, Pillow-decoded dumps and hand-built 16-bit and top-down files. Not supported (typed error): JPEG/PNG-in-BMP, OS/2 Huffman and RLE24.
  - TGA: types 1/2/3/9/10/11, 8/15/16/24/32 bpp, all four origins; encoder writes 24/32-bit or 8-bit gray, raw or RLE. Checked against 16 Pillow-written files and hand-built 15/16-bit and right-to-left files.
  - GIF: first frame of 87a/89a files (interlaced, local/global palettes, transparency; later frames are skipped with a note, since the image model has no frames yet); encoder writes an exact palette up to 256 colours, otherwise median-cut with optional Floyd-Steinberg dithering, with loss notes for quantisation and for rounding partial alpha. Checked against 9 Pillow-written files; our files open in Pillow and ImageMagick. The shared quantiser is in `oc-image::quant`.
  - JPEG: decoder for baseline, extended-sequential and progressive Huffman files, 1/3/4 components, any integral chroma subsampling, restart intervals, JFIF dpi, ICC profiles, Adobe RGB/YCCK/CMYK. It uses libjpeg's integer IDCT, fancy upsampling and fixed-point colour maths, and its output is byte-identical to libjpeg (via Pillow) on all 24 fixtures: 4:4:4, 4:2:2, 4:2:0, 4:4:0, progressive, optimised tables, restart markers by block and by row, gray, CMYK, quality 10 and 100, sizes from 1x1 to 131x97. Truncated data decodes as far as it goes with a warning. Encoder: baseline with the standard tables, 4:4:4/4:2:2/4:2:0, quality 1-100; file sizes are within 5% of libjpeg's and PSNR within 0.3 dB on the same input, and libjpeg decodes our files to exactly the pixels our own decoder gives. Also reads arithmetic-coded files (sequential and progressive, DAC conditioning; `jpeg::decode::arith`, state table read back from libjpeg by `tools/gen_arith_table.py`), 12-bit DCT files (to 16-bit output, libjpeg's 12-bit IDCT and colour tables) and lossless SOF3 files (predictors 1-7, point transform, restart intervals, 2-16 bit precision, 1/3 components without subsampling; 3-component lossless is RGB unless JFIF or Adobe transform 1 says YCbCr, as libjpeg-turbo's lossless mode also skips colour conversion). Bit-identical to libjpeg-turbo 2.1.5 on 13 arithmetic files (`tools/make_jpeg_arith_fixtures.py`) and to libjpeg-turbo 3.2 on 36 12-bit and lossless files (`tools/make_jpeg_deep_fixtures.py`). Not supported (typed error): hierarchical and arithmetic-lossless JPEG, lossless with subsampling, 12-bit or 16-bit CMYK, non-integral subsampling ratios. EXIF orientation is reported in a note and not applied. `optimize` builds the Huffman tables from the picture (Annex K.2 length limiting) and `progressive` writes libjpeg's default ten-scan progressive script (successive approximation, EOB runs, refinement bits); on 4:4:4 the file sizes equal libjpeg's byte for byte (Pillow, same quality), on 4:2:0 they are within 4% (progressive 0.2%), and libjpeg decodes both to the same pixels as our decoder. `trellis` picks quantised values by rate-distortion cost (dynamic programming over the last non-zero position, standard-table code lengths as the price): 5 to 20% smaller at equal PSNR on three test pictures. `lossless` (with `rotate`/`flip`, JPEG to JPEG) works on the quantised coefficients without decoding (`jpeg::transform`: mirror, transpose, rotate, MCU-aligned crop; quantiser tables follow a transpose; mirrors trim partial edge blocks with a Loss note; JFIF/Exif/ICC/Adobe/comment segments are kept; output uses optimised tables, progressive if the input was or `progressive` is set); pixel-identical to jpegtran 2.1.5 `-trim` on 69 cases (4:4:4, 4:2:0, 4:2:2, 4:4:0, gray, progressive, odd sizes; `tools/make_jpeg_transform_fixtures.py`). Fuzz targets `jpeg` and `jpeg_transform`. Not done: arithmetic coding on output, restart markers on output, EXIF orientation reset after a lossless turn.
  - ICO/CUR: reads the largest image, stored as PNG or as a DIB (1/4/8/24/32-bit, with the AND mask, and old 32-bit icons whose alpha byte is unused); writes PNG-compressed entries at the requested square sizes (`sizes=16,32,48,256`), or the image's own size, for ICO and CUR (hotspot 0,0). Checked against 5 Pillow/ImageMagick files; Pillow and ImageMagick read ours. Not done: choosing which size to read, writing DIB entries for pre-Vista readers, ICNS.
  - TIFF (`tif`/`tiff`, little and big endian, classic and BigTIFF): reads strips and tiles, none/LZW/Deflate/PackBits and CCITT fax (Modified Huffman, Group 3 in 1D and 2D with or without fill bits, Group 4; `oc-image::ccitt`, code tables read back from libtiff by `tools/gen_ccitt_tables.py`), horizontal predictor (8 and 16 bit), bilevel/gray/palette/RGB/RGBA/CMYK (converted to RGB with a note), 1-16 bits per sample, extra alpha (unpremultiplied with a note), dpi and ICC; first page only (note), orientation reported not applied, truncated data decodes as far as it goes with a warning. Writer: gray/gray+alpha/RGB/RGBA at 8 or 16 bits, `compression=none|lzw|deflate|packbits` (default lzw) and `predictor` (default on), dpi and ICC. Compression 7 (new-style JPEG in strips or tiles, shared `JPEGTables` or self-contained, gray, RGB and YCbCr with any subsampling) goes through the JPEG decoder. Pixel-identical to libtiff (via ImageMagick) on 88 fixtures (9 BigTIFF, 33 fax, 14 JPEG); Pillow and ImageMagick read our files. Not done: BigTIFF, CCITT and JPEG writing, old-style JPEG (6), CMYK JPEG, tiled output, multi-page output, fax uncompressed mode.
  - WebP (`webp`): lossless (VP8L) and lossy (VP8 key frames, in the new `oc-vp8` crate). Lossless: the full decoder (all four transforms, colour cache, meta prefix images, LZ77 with the 2-D distance map, simple and normal prefix codes, ICC from an extended header) is pixel-identical to libwebp (via Pillow) on 27 files made with methods 0-6, qualities 0-100, palettes of 2-256 colours, alpha with and without `exact`, and sizes from 1x1 to 262x194. The encoder writes subtract-green, per-tile predictors chosen against the running residual statistics (libwebp's approach, with its near-zero bias), per-tile cross-colour multipliers, palettes with 1/2/4/8-bit pixel packing, hash-chain LZ77 with a cost-model parse, a colour cache sized by estimate, and tile-wise prefix code groups from clustering; `effort` 0-6 and `clean_transparent` are the options. Our output decodes to the identical pixels in libwebp (Pillow) in 259 of 259 combinations (27 fixtures, random and structured pictures, efforts 0-6, 1xN/Nx1/gray/palette inputs). Size against libwebp at its default method 4 on six pictures (800x600 screenshots, noisy and smooth 1-2 MP photographs): +0.5% in total at effort 4 (screenshots +1-3%, noisy photo +2.8%, smooth photo -3%) and +1.3% against its method 6 at our effort 6. Speed: a 1.9 MP photograph encodes in about 1.0 s at effort 4 and decodes in about 0.1 s. A fuzz target covers the decoder and another the encoder round trip.
    Lossy decode: `oc-vp8` implements RFC 6386 key frames (boolean decoder, segments, token partitions, all intra modes, the WHT and DCT, simple and normal loop filters) and matches libwebp's `WebPDecodeYUV` plane for plane on 51 files made by libwebp through Pillow and ImageMagick (qualities 5-100, methods 0-6, 1-4 segments, 1-8 partitions, filter type, strength and sharpness variants, sizes 1x1 to 200x150). `oc-image` adds libwebp's fancy chroma upsampling and its integer YUV to RGB, plus `ALPH` (raw or lossless-coded, all four prediction filters), and is pixel-identical to Pillow on 36 more files including alpha. The tables of the format were read once from a libwebp binary by a documented script (ADR-0004).
    Lossy encode (`lossless=false`, `quality` 0-100, `effort` 0-6): RGB to 4:2:0 with libwebp's coefficients, per-macroblock choice between four 16x16 modes and ten 4x4 modes per sub-block by distortion plus an estimated rate taken from the token probabilities that end up in the stream (a second pass refines the estimate at effort 4 and up), dead-zone quantisation, optimal probability updates, skip flags, 1-8 token partitions, and a loop-filter level searched by reconstruction error. Alpha goes in an `ALPH` chunk coded with the VP8L encoder and the best of four prediction filters; fully transparent 8x8 blocks are flattened. The decoder reproduces the encoder's own reconstruction exactly, and libwebp (via Pillow) decodes our files, alpha exactly. Against libwebp at equal PSNR on six pictures (three screenshots, three photographs) at qualities 15-90, our files are 4.0% smaller than its method 4 and 2.5% smaller than its method 6 (screenshots -6% to +1.5%, photographs -3% to -8%). A 1.9 MP photograph encodes in about 0.6 s at effort 4 including the PNG decode. Fuzzing: `vp8` (raw key frames) and `webp_lossy_roundtrip` ran 90-120 s each; the first run found an integer overflow in the inverse DCT on corrupt coefficients, now wrapping like libwebp's C code.
    Not done: EXIF/XMP carry-over, trellis quantisation and per-segment quantisers (libwebp's SNS) in the lossy encoder, lossy alpha (`alpha_quality`), a palette-ordering search beyond first-seen and sorted and predictor transform on palette indices in the lossless one.
  - QOI and Netpbm (P1-P7; writer picks PBM/PGM/PPM/PAM from the output extension, PAM when there is real transparency).
  - Animation (`oc-image::anim`: an `Animation` is full-canvas RGBA frames, delays in ms, a loop count). Read: GIF (disposal 0-3, transparency, Netscape loops), APNG (dispose and blend ops, a default image that is not part of the animation) and animated WebP (ANMF dispose and blend, lossless and lossy frames, alpha); every frame is composited to the canvas as it is shown. Write: GIF and WebP keep an animation whenever the output can hold one, APNG when the output extension is `.apng` (a `.png` stays a still). Encoders store only the rectangle that changed since the previous frame (GIF marks unchanged pixels transparent and clears with disposal 2 when pixels become transparent again; APNG and WebP replace the rectangle, WebP with even corners). `frames=first` keeps only the first frame; width, height, rotate and flip apply to every frame. Decoded frames match Pillow's on 28 files (GIF with all four disposals, with and without transparency, APNG with dispose 0-2 and blend 0-1, WebP lossless, lossy and mixed); Pillow and ImageMagick read our GIF, APNG and WebP animations with identical frames and delays. Fuzzing: `animation` (the three readers) 60 s and `animation_roundtrip` 90 s, no findings. Not done: palette sharing across GIF frames (each frame has its own table), merging identical consecutive frames, blend-over optimisation in APNG/WebP, 16-bit APNG frames (composited at 8 bits with a loss note).
  - ICNS (`oc-image::icns`): reads the largest image from PNG entries (icp4-icp6, ic07-ic14, Retina sizes judged by the PNG's own width) or the old RLE RGB entries with their 8-bit masks (is32, il32, ih32, it32); identical to Pillow on 7 files (the legacy ones built by `tools/make_icns_fixtures.py`, whose RLE Pillow decodes independently). Writes PNG entries at 16-1024 (`sizes`, default the standard sizes that fit the image), read back by Pillow. JPEG 2000 entries and the palette forms (icl8, ics4 and the like) are named as unsupported; uncompressed RGB entries are not recognised because Pillow and the spec disagree on their layout. Fuzz target `icns`.
  - DDS (`oc-image::dds`): reads the first surface of uncompressed formats with any channel masks (8/16/24/32 bit, luminance, alpha-only, DX10 B8G8R8A8/R8G8B8A8/B5G6R5/B5G5R5A1/R8/A8) and BC1-BC5 (DXT1-5, ATI1/2, DX10 typeless and sRGB variants) BC6H (all fourteen modes, signed and unsigned, `oc-image::bc6h`; shown as clipped sRGB with a note; bit-exact against bcdec on 30 random-block fixtures via `tools/make_bc6h_fixtures.py`) and BC7 (all eight modes, `oc-image::bc7`; partition tables read back from Pillow by `tools/gen_bc7_tables.py`); BC4 becomes gray, BC5 red-green. Identical to Pillow on 33 files (nine of them random BC7 blocks covering every mode), including ImageMagick's squish-made DXT1/DXT5 with punch-through alpha and sizes that are not a multiple of 4. Writes BGRA8, BC1 or BC3 (principal-axis endpoint fit, nearest-colour indices); Pillow and ImageMagick read ours. Not done: BC7 and BC6H encoding, signed BC4/BC5, float and 16-bit formats, writing mipmaps (only the top level is written), BC5 and BC4 output. Fuzz target `dds`.
  - PSD / PSB (`oc-image::psd`): reads the merged image of bitmap, gray, duotone (as gray), indexed, RGB and CMYK files at 1, 8 and 16 bits, raw / RLE / ZIP (with and without prediction) coded, first extra channel as alpha, ICC profile and resolution; layers are not read. Identical to Pillow (8-bit) and ImageMagick (16-bit, PSB, CMYK, indexed) on 11 files. Writes gray, gray+alpha, RGB and RGBA at 8 or 16 bits, RLE or raw, PSD or PSB by extension; Pillow and ImageMagick read ours. The ZIP forms and the bitmap mode are covered only by the format description (no tool here writes them). Not done: Lab and multichannel modes, 32-bit float, layer reading, duotone curves. Fuzz target `psd`.
  - Radiance HDR (`oc-image::hdr`): reads RGBE and XYZE with flat, old-run and new-RLE scanlines in all eight orientations, writes RGBE with new RLE (flat when the width is under 8 or over 32767). The model has no float depth, so reading clips to [0, 1] and encodes sRGB, and writing converts sRGB to linear radiance; both say so in a note. EXPOSURE is ignored. Identical (within one code value) to an independent float64 reader on 20 files, including one written by ImageMagick; ImageMagick reads ours back (it treats the stored values as display values, which is why the check there is against linear radiance). Fuzz target `hdr`.
  - Colour management (`oc-image::icc`, M2.1): reads ICC v2 and v4 RGB matrix/TRC, gray and LUT profiles (`mft1`, `mft2`, `mAB `; RGB, gray and CMYK; XYZ or Lab PCS; `curv` and `para` types 0-4) and converts to sRGB with relative colorimetric, perceptual or saturation intent and black point compensation (always on for perceptual and saturation, as in Little CMS). Matches Little CMS (via Pillow's ImageCms, optimisation off) within 2 code values on 28 hand-built profiles x 3 intent/compensation settings, except CMYK output profiles with compensation (up to 9: Little CMS finds their black point through the B2A0 table, which we do not read). Engine policy (`profile` option): `keep` stores the profile where the format can (PNG, JPEG, WebP, TIFF, PSD) and otherwise converts the pixels to sRGB with a note; `srgb` always converts; `strip` drops it. A profile that cannot be read is dropped with a warning. CMYK JPEG with an embedded CMYK profile is converted with it on decode. An sRGB-like profile is detected and left alone. Not done: B2A tables and conversion to a profile other than sRGB, named colour and abstract profiles, CICP (PNG cICP, HEIF), HDR tone mapping, colour management for animation frames. Fuzz target `icc`.
  - OpenEXR (`oc-image::exr`): reads scanline and tiled files (first mip level) with half, float and uint channels in RGB, RGBA, Y and Y+A, compressed with none, RLE, ZIPS, ZIP, PIZ (own Huffman and wavelet code), PXR24 and B44/B44A; writes half floats (RGB, RGBA, gray, gray+alpha; none, RLE or ZIP). As with HDR, reading clips to [0, 1] and encodes sRGB (alpha un-premultiplied) and writing converts sRGB to linear (colour premultiplied), both noted. Identical (within one code value) to the OpenEXR library's own decode on 86 files covering every compression, sizes from 1x1 to 130x17, 16-bit-wide dynamic range, tiles and alpha; the library reads our output back to within half-float precision. Not done: DWAA/DWAB/HTJ2K, deep and multi-part files, subsampled (luma/chroma) channels, mip levels other than the first, B44 with perceptually linear channels, tiled output. Fuzz target `exr`.
- [~] M2.5 engine and CLI: `openconverter convert a.png b.bmp` (and between png, bmp, tga, qoi, pnm, gif, jpeg, ico, icns, dds, psd, hdr, exr, tiff, webp) work end to end, through the worker process. Writer options: `width`, `height`, `rotate`, `flip`, `background`, `frames` (animations), `profile`/`intent` (colour profile handling), plus `level`/`adaptive_filter` (PNG), `rle` (TGA, PSD), `ascii` (Netpbm), `dither`/`interlace` (GIF), `quality`/`subsampling` (JPEG), `sizes` (ICO, ICNS), `compression` (TIFF, DDS, EXR), `predictor` (TIFF), `lossless`/`quality`/`effort`/`clean_transparent` (WebP). The file's content wins over its extension (mismatch is a warning). Metadata that the target cannot hold is reported as a loss note. Tested by converting every format pair through the engine and by checking CLI output with Pillow and ImageMagick.
- [~] Fuzzing: targets for png, bmp, tga, qoi, netpbm and an image round trip, seeded with the fixtures and run for 40-60 s each locally without a crash. The nightly workflow lists them but has not run.
- Performance has not been measured: layout conversion costs roughly 100 ns per pixel in debug builds, and a 1.8 MP BMP takes about 0.4 s to decode in a fuzz build. Release-build timings on a 3 MP picture: PNG to JPEG 0.2 s, JPEG to PNG 1.7 s (PNG encoding at level 6 dominates), PNG to BMP 0.17 s. That is acceptable for correctness work and is to be fixed in the performance milestones (SIMD, M1.2 leftovers).

## Phase 4: Audio
Format notes are in [formats/](formats/README.md). Interop checks (ffmpeg, libopus, libmpg123 as oracles at test time only) are in `tools/audio_interop.py`: 94 checks, all passing.
- [~] M4.1 DSP (`oc-audio::dsp`): sample-format conversion with none/TPDF/shaped dither, channel mixing with BS.775 downmix, a polyphase Kaiser-window sinc resampler (four quality presets), BS.1770 / R128 integrated loudness, range and true peak, normalisation, ReplayGain tags, trim, fades, silence trimming. Normalising reaches the target within 0.3 LU as ffmpeg's ebur128 measures it.
- [~] M4.2 PCM containers: WAV (RIFF, RF64, BW64, extensible, float, A-law, mu-law, LIST/INFO), AIFF/AIFF-C (including `sowt`, float, 80-bit rates), CAF; FLAC encoder and decoder (levels 0-8, MD5 checked, bit-identical to ffmpeg, within 3% of its size). Not done: WAV ADPCM and `bext`/`cue ` chunks, AIFF markers and ID3 chunk, FLAC CUESHEET, Ogg FLAC.
- [~] M4.3 MP3: layer III decoder (matches ffmpeg and libmpg123 to 3e-6) and encoder (CBR/VBR, bit reservoir, Xing/LAME header, ID3v2.4), ID3v1/v2.2-2.4 and APEv2 tags. Not done: layers I and II, a psychoacoustic model and short blocks in the encoder, ABR, VBRI.
- [~] M4.4 Ogg, Vorbis and Opus: Ogg pages; Vorbis decoder (matches ffmpeg to 5e-8) and encoder (within a few percent of libvorbis in size and SNR); Opus CELT decoder (range-coder state identical to libopus on 12 streams, 70-85 dB SNR) and encoder (CBR/VBR/CVBR, 2.5-20 ms, multichannel; libopus decodes it). Not done: Opus SILK and hybrid decoding and encoding (ADR-0008), Vorbis short blocks and floor 0.
- [~] M4.5 Tags, cover art and containers: one tag model for Vorbis comments, ID3, MP4 atoms, APEv2 and Matroska ([formats/tags.md](formats/tags.md)); ALAC (bit-exact with ffmpeg) in M4A and CAF on a shared ISO-BMFF reader; Matroska/WebM reader and writer in `oc-container` (EBML, lacing, unknown-size clusters, tags, chapters, attachments) with audio in `.mka`/`.weba` (Opus, Vorbis, FLAC, PCM; reads MP3 too); lossless stream copy between Ogg, Matroska/WebM and FLAC (ADR-0009). Not done: AAC and AC-3 (ADR-0006), ALAC in Matroska, MP3 packets into Matroska, stream copy for M4A and CAF.
- [~] M4.6 Audio UI: waveform from the decoded samples, integrated loudness, loudness range, sample and true peak, tags, playback of the first 90 s (the original, or a WAV made by the worker), nine built-in presets (Podcast: Opus 64 kbps mono at -16 LUFS, Voice memo, Music small, Music compatible, Streaming, Web audio, Lossless archive, Apple Lossless, CD quality). Endpoints `/api/files/{id}/audio`, `.../audio.wav` and the same under `/api/outputs/`. Driven in headless Chromium: preset, waveform, convert, output waveform. Not done: user-defined presets, seeking by dragging, per-channel waveforms.
- Fuzz targets: `flac`, `vorbis`, `mp3`, `alac`, `opus`, `matroska`, `audio_wav_aiff`, run 45 s each locally; the nightly workflow lists them.
- Not run on a real machine: the desktop shell's audio playback (WebKitGTK codec support varies; the WAV preview exists for that reason).

## Known gaps
- 1.x Python test cases are not ported yet; they are available at tag v1.0.0. Port them as each Rust codec lands (M1.x, M2.x).
- cargo-deny passes locally (advisories, bans, licenses, sources); the Tauri tree is allowed through named wrappers (ADR-0005).

- [~] M2.6 serve mode and desktop app. `openconverter serve` (crates `oc-server`, axum 0.8 on loopback with a per-run option for a token): upload (own streaming multipart parser, because axum's multipart pulls a banned crate), format list with option schemas, jobs with progress over server-sent events and cancellation, outputs, previews (thumbnails from sandboxed workers), history with retention, settings; the shared UI in `ui/` is embedded in the binary. Security: Host allow-list, CSRF header plus Origin check, strict CSP, no remote bind without `--allow-remote` and a token. Documented in [API.md](API.md); `crates/oc-server/tests/ui_safety.rs` keeps innerHTML, inline scripts and remote URLs out of `ui/`; 3 end-to-end tests drive the real binary. Desktop (`oc-desktop`, Tauri v2): a window on the embedded server (ADR-0005), icons, bundle config; renders the UI under Xvfb. Not done: single-instance and file arguments, native file dialogs, "show in folder".
- [~] M2.7 packaging: `cargo xtask deb|sbom|checksums`, and `.github/workflows/release.yml` (musl and macOS and Windows CLI archives, Tauri bundles: .deb, .rpm, AppImage, NSIS, MSI, dmg, a portable Windows zip; CycloneDX SBOM and SHA256SUMS). Only the .deb, SBOM and checksums were built here; the workflow itself has never run, and the Windows installers need the MSVC toolchain.
- [~] M2.8 [COMPATIBILITY.md](COMPATIBILITY.md) is generated from the registry by `tools/gen_compat.py`; screenshots of the UI are in `docs/screenshots/`.
